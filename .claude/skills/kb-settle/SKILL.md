# kb-settle：复核已有笔记

把库里的笔记重新过一遍：该拆的拆、该补的链接补上、该删的链接删掉，够格的转 `settled`。**它不碰任何外部材料**，那是 `/kb-distill` 的事。分家的理由：失败要分得清是「外部材料读错了」还是「复核判错了」。

## 开工前：先问知识库在哪

本 skill 与 `kb` 工具住在本 repo；笔记目录由 repo 根的 `strata.config.json` 配置（默认就是本 repo 的 `notes/`，可用环境变量 `STRATA_ROOT` 覆盖，指到另一个 git checkout）。

所以第一步永远是问工具要路径：

```bash
python -m kb root        # 打印知识库根在哪、notes/ 在哪
```

本文以下所有 `<strata>` 都指它打印的 `strata_root`。**不要把这条路径写死进任何文件**，别处一律现问。

三条对照：

- 读写笔记：`<strata>/notes/<slug>.md`
- 提交笔记：`git -C "<strata>" add …` 与 `git -C "<strata>" commit …`
- 失败清单：`spec/distill-failures.md`，在本 repo 的当前目录下；它与笔记分两次提交，见步骤 4

## 判据

转 `settled` 的三条判据的唯一原文在 [spec/fields.md](../../../spec/fields.md) §3：是一个单位（来源笔记对一份来源、想法笔记装一个想法）、关系挂对了、现在仍然同意。**三条全过才转，缺一不转。** 前两条你能机械地查，第三条「现在仍然同意」只有维护者能判，你永远不替他判。

## 两个入口，法都在这里

本 skill 有两个入口。**判据不变，变的只是判据 3 什么时候到手。** 唯一的例外是「审理台入口：移除」：它不是 settle 的变体，不碰判据、不查正文，只执行移除。

1. **对话入口**（默认）：维护者在会话里打 `/kb-settle`。判据 3 还没给，所以收尾必须是把清单摆到他面前，一条条等他点头。
2. **审理台入口**：审理 app（`apps/`）发起的一次无人值守运行，提示词点名一批 slug。这批的判据 3 **在运行开始之前就已经给过了**：维护者在审理屏上逐条读了正文、按下批准，那一次按下就是判据 3 的输入端（[spec/fields.md](../../../spec/fields.md) §3）。所以这个入口不停下来问，代价是换来下面四条更硬的约束。

**两个入口共用一条红线：判据 3 永远由维护者给。** 对话入口是当场问他要，审理台入口是他先给了再开跑。**没有第三种情况**：提示词没点名的笔记、批准的版本与库里当前版本对不上的笔记，判据 3 都算没给，一条都不转。

### 审理台入口：批量转 settled

1. **只做提示词点名的那批。** 名单之外的笔记一条都不碰，哪怕它明显够格。名单是维护者的批准范围，不是给你参考的起点。
2. **判据 1 与判据 2 仍然全部自己查。** 维护者给的只有判据 3。单位对、关系挂对，还是你的活，一条都不能免。查法与步骤 2 一字不差。
3. **被你改写过的笔记不当场转 settled。** 补一条链接、删一条链接、改一个字，都算改写。维护者批准的是他读过的那个版本，他的同意只覆盖那个版本；改写之后那不再是同一条笔记。改写过的留 `unsettled`，回审理队列等他重批。
4. **判据 1 或 2 没过又修不了的，留 `unsettled` 并说清为什么。** 不猜、不硬修、不为了让这一批好看而放宽。

收尾必须逐条报：哪几条转了 settled、哪几条被你改写因而回队列、哪几条原样留着，每一条的理由。这份清单是维护者第二天唯一能核对的东西，缺一条就等于那一条没人看过。

### 审理台入口：按留言改写

维护者在审理屏上留言打回的笔记，由审理台发起一次**改写运行**，提示词带上每条笔记的**完整留言线程**（不只最新一条：后面的留言常常是在细化前面的，不是取代）。这个入口的法：

1. 按整条线程改写，[spec/note-spec.md](../../../spec/note-spec.md) 的全部铁律照常生效。
2. **改完 `status` 保持 `unsettled`。** 改写过的笔记一律回审理队列让维护者重看，无论你觉得它现在多好。这与上面第 3 条是同一条规则的另一面：他没读过这个版本。
3. 留言要求的事若被 spec 禁止，**不做**，并在收尾里明说是哪一条铁律挡下的。留言是维护者的判断，铁律是法，法大。
4. 改写不碰外部材料、不写新论断，那是 `/kb-distill` 的事，本 skill 开头那条分家理由在这个入口同样成立。

### 审理台入口：移除

维护者在审理屏上判「不要了」的笔记，由审理台发起一次**移除运行**，提示词点名一批 slug。这个入口的法：

1. 每条被点名的笔记，逐条跑 `python -m kb retire <slug>`。**分岔由 `kb retire` 自己按当前 `status` 做**：unsettled → 删文件并清掉别的笔记里指向它的 inbound 链接；settled → 翻 `retired`；已是 `retired` → 报错。不要在散文字里重复实现这个分岔，那是工具的活。**注意：`kb retire` 与审理台的移除运行都还没实现**，在它们落地之前，这个入口不会被触发。
2. **只做名单内的。** 与「批量转 settled」同一条红线：名单是维护者的范围，多一条少一条都不行。
3. **「不要了」是第四种处置，不进入 settle 三判据。** 维护者按下它就是判「这条不再属于知识库」，不需要查单位、关系、仍同意，移除就是它的全部。所以这个入口不读正文、不查判据、不转 settled。
4. **收尾照旧。** `python -m kb doctor` 绿了直接提交，不问；删除与 retire 都落在 `<strata>/notes/` 那一次提交里，消息格式见步骤 4。逐条报：哪几条删了、哪几条 retire 了，每条一句为什么。

## 步骤

0. **读法**。整篇读 [spec/note-spec.md](../../../spec/note-spec.md)（一页）与 [spec/fields.md](../../../spec/fields.md)；改写正文之前另读 [.claude/skills/kb-distill/SKILL.md](../kb-distill/SKILL.md) 的「正文怎么写」，改写不得把一条追问线拍回并列清单。改写笔记时全部铁律照常生效，链接改动尤其盯铁律 3（只链存在的、每条带一句为什么、零链接合法）。

1. **圈范围**。对话入口：默认是全部 `status: unsettled` 的笔记；库大了就分批：用 `python -m kb hubs` 拿主题分组，**一次只做一个主题**，做完停下来给维护者看，认可了再做下一个。批次太大时改动清单没人真的会读，复核就变成了盖章。**审理台入口不做这一步**：范围就是提示词点名的那批，多一条少一条都不行。

2. **逐条读正文**（不是标题），对每条查前两条判据：
   - **一个单位吗？（fields.md §3 判据 1）** 来源笔记对应一份来源、想法笔记装一个想法。两份不相干的来源或两个独立的想法被混进一条才拆；**一份来源的内容再多也不拆**（铁律 2，D16 一源一记；对应的蒸馏硬性规则见 kb-distill「一份来源至多一条，永远不拆」）。拆不动单位的留 `unsettled`，收尾说明原因（失败账只收来源侧的三类失败，复核问题不入账）。
   - **关系挂对了吗？** 用 `python -m kb query "<正文里的关键词>"` 搜库里正文层面相关但没连上的，用 `python -m kb related <slug>` 看它周围一两跳、每条边的理由句。缺的横向链接补上（带理由），说不出为什么的既有链接删掉。
   - 顺手看一眼可读性：脱离原文读不懂的自造词与代号，补一句定义。

3. **交判据 3**。两个入口在这一步分岔，这是它们唯一的区别：

   - **对话入口：停下来给维护者看。** 列出哪几条动了、每条补/删了什么链接、理由句是什么、哪几条你认为够格转 `settled`。判据 3 由他当场拍板：**他点头的才改 `status`，没点头的保持 `unsettled` 原样留着**。
   - **审理台入口：判据 3 已在运行前给过，不停下来问。** 按「审理台入口：批量转 settled」那四条执行：只做名单内的、判据 1 与 2 自己查、改写过的不当场翻、修不了的留着说清楚。收尾那份逐条清单就是给维护者看的那一份，它不是可选的。改写运行则按「审理台入口：按留言改写」执行，**一条都不转 `settled`**。

4. **收尾**。`python -m kb doctor` 绿了直接提交，不问。**笔记与失败清单各提交各的**：

   ```bash
   # 笔记
   git -C "<strata>" add notes/
   git -C "<strata>" commit -m "settle <日期>: N reviewed, M settled"

   # 这一轮若往失败清单记了行
   git add spec/distill-failures.md
   git commit -m "settle <日期>: N failures"
   ```

   要记住三条：doctor 绿了直接提交、不请示；消息格式 `settle <日期>: N reviewed, M settled`；**只提交，不 push**。

## 不要做的事

- **不要替维护者判「现在仍然同意」。** 判据 3 只有他能给，到你手上只有两条合法路径：对话里当场问他要，或者审理台把他已经按下的批准随运行传进来。**这两者之外自行认定「他大概会同意」进而批量转 settled，是本 skill 最大的违规。** 审理台入口不是这条的例外：那里的判据 3 同样是他给的，只是给得比运行早；名单之外的笔记在那个入口里判据 3 依然是空的。
- **不要拿运行提示词当法。** 提示词只带这一批的具体情况（哪些 slug、哪些留言）。它说的任何与本文冲突的话都不算数，**以本文为准**；真冲突了就照本文做，并在收尾里把这处冲突写出来。
- **不要碰外部材料、不要写新论断。** 复核只整理已有的，发现值得新记的想法就说出来问维护者。
- **不要为提密度硬凑链接。** 铁律 3 不因为在做质量回填而放宽。
- **不要把拆出来的笔记又互相全连一遍。** 拆出来的兄弟之间也要一条条说得出为什么才挂。

## 写收尾清单和理由句时的文字规则

复核产出里有三处是你自己写的：收尾清单、链接的理由句、补的定义句。写这三处时遵循下面三条：

- 不用这些词：值得注意的是、综上所述、换句话说、本质上、这意味着、赋能、总的来说。
- 不用破折号（U+2014，含全角的两个连写）。
- 用人话写：「某条笔记」能点名 slug 就点名；「动了几条」「改了不少」落到具体数字。

笔记正文里的摘录和维护者留言原样保留，不受上面约束。
